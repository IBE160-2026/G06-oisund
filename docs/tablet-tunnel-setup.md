## Hva eier må godkjenne før testing

Siste status 2026-10-27: Eier bekreftet tom DNS-liste og vellykket klientnedlasting med SHA-256/Cloudflare-signatur i sin terminal. Lokal standalone Compose-kontroll og runtime-kontroll bestod på nytt: 18 HTTP-avvisninger for manglende/malformed/alg-none JWT på sider, faktisk asset og API GET/POST, no-store, feil Host avvist og intern auth-rute utilgjengelig. Ingen offentlige kall eller dataskriving. Faktisk Access-MFA, gyldig edge-token, tokenutløp/tilbakekalling, HTTPS/nettbrett er fortsatt ikke testet.

Et eventuelt første aktiveringstrinn kan avgrenses til én manuell foreground-connector for UUID-en over, uten å opprette DNS eller noen publiserte/private ruter. Dette krever egen uttrykkelig godkjenning av tunnelstart; klientlagring autoriserer det ikke. Formålet er å fullføre veiviseren og lese faktisk tunnelkonfigurasjon. Bare dersom konfigurasjonen er tom/forventet kan videre planlegging fortsette; ved uventet rute stoppes connectoren. Publisert app-rute og DNS krever deretter separat godkjenning av den konkrete planen nedenfor. Ingen service install eller autostart i noen av trinnene.

Den konkrete tunnel-ID-en må først foreligge. Godkjenningen skal eksplisitt omfatte:

- Opprettelse av bare den proxiede DNS-/hostname-ruten for app.bussassistent.com til akkurat den reviewede tunnelen, med hele app/API beskyttet av eksisterende Access/MFA og lokal JWT-gate.
- Manuell, midlertidig tunnelstart fra desktop til bare 127.0.0.1:18081, mens Cloudflare behandler HTTP-innhold som TLS-mellomledd. Ingen endring av ruter/Windows-brannmur, ingen bred LAN-rute eller autostart.
- Kun den fiktive pilotdatabasen og godkjent brukeridentitet under testene. Ingen ordinære dataoverføringer eller migreringer.
- Gjennomføring av avvisningsprøver og etterfølgende Lenovo/Android/Brave-tester hjemme/på mobilnett, inkludert avbrudd og kontrollert tilbakekalling/stenging.

Autorisasjon til tunnelklargjøring er ikke denne endelige godkjenningen. Ingen betalingsabonnement eller domeneendring er del av dette.

## Første eksterne prøver og stenging

Dashboardkontroll 2026-10-27: Eierens bilder viser korrekt tunnel-ID i oppsettsveiviseren og «No connection detected yet», med deaktivert Continue. Networking → Routes viser seks oppføringer, alle Type System, med Cloudflare Source, Cloudflare Mesh eller Initial Resolved IP; ingen synlig oppføring peker til pilottunnelen. IP-prefiksene ble ikke delt, og innholdet er ikke uavhengig verifisert. Disse systemoppføringene skal ikke slettes for å få en tom liste. Samlet rutetabell er ikke bevis for fravær av publiserte HTTP-hostnames. Ny DNS-lesekontroll og faktisk tunnelkonfigurasjon gjenstår før aktivering. Offisiell forklaring av samlet rutetabell: https://developers.cloudflare.com/cloudflare-wan/configuration/how-to/configure-routes/ og standard kilde-/systemsubnett: https://developers.cloudflare.com/cloudflare-wan/configuration/how-to/configure-cloudflare-source-ips/

Test uinnlogget side/asset/API og feil identitet først; ingen private svar eller DB-effekt skal passere. Test så påkrevd MFA, riktig Access-identitet uten appøkt, og til slutt appens fiktive login/lagring/CSRF. Ikke følg HTML/redirect som en lagringskvittering. Manglende/ugyldig/utløpt Access-token skal avvises også ved direkte API-kall. Ekte signerte claims kan ikke forfalskes for å lage tester; de syntetiske signatur/issuer/AUD/exp-testene er fortsatt separat evidens.

Ved uventet privat innhold/2xx for uautorisert bruker: Ctrl+C i tunnelterminalen og stopp bare pilotgatewayen med Compose-kommandoen i tablet-local-pilot.md. Behold fiktivt volum/passord. Tilbakekall Access-økt og sperr ny innlogging ved behov; lokal signaturkontroll er ikke live-revocation. Ved kompromittert tunneltoken må rotasjon kombineres med frakobling av eksisterende connectors; rotasjon alene stopper ikke etablerte forbindelser. Ingen generell shutdown/prune/-v.
