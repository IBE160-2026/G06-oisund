## Proposed text

The project began with a broad idea for a driver's assistant. The delivered SCOPE-02 V1 is narrower: it imports supported text PDFs, allows explicit correction and saving, confirms a saved plan, and supports manual activity selection, shift status and source-linked notices. GPS, automatic notices, live progress and the other planned extensions are outside this delivery. Completed Ubuntu operations are also included in final V1 under the later owner decision. This boundary makes it possible to explain and test what the application actually does without presenting an unimplemented vision as a finished result.

Jonas supplied the use case, interpretation of source documents, scope decisions and acceptance decisions. AI assisted with analysis, specifications, architecture, code, synthetic tests, documentation and review. The important quality controls were independent expected facts, actual API/PostgreSQL checks, preserved failures and explicit human assessment. The record does not measure hours saved, prompt counts or percentages of authorship, so no such numbers are claimed.

The distinction between technical verification and acceptable use became visible during12.4. Passing tests did not settle the workflow: Jonas withheld acceptance because review was repetitive, correct imports still forced editing, bus saving was awkward and feedback involved scrolling. The subsequent correction and actual owner acceptance show why a green test result cannot make a subjective product decision. They also informed the adopted practice of reviewing the whole flow early and recording actual labels, feedback and touch observations before the final integration gate. [12.4 correction and acceptance](../evidence/12-4-import-experience.md).

The D1–D3 follow-up exposed a related problem in failure handling. A known rejected write and an unknown current saved state are different facts. A lost response can leave a successful server write uncertain, while a deleted parent plan can make further resolution impossible. The corrected flow retains the original operation, avoids an automatic resend and allows deliberate abandonment only after fresh authority checks. Personal Lenovo testing included cancelling and then confirming that action; the message says that saving has not been confirmed. Showing explicit UTC offsets also distinguishes the two Oslo02:30 occurrences without changing stored instants. These are concrete examples of making uncertainty visible rather than replacing it with a plausible answer. [D1–D3 owner record](../evidence/v1-acceptance-2026-10-29.md).

Testing itself required scrutiny. A manual-test helper initially could not receive commands, and a later helper needed an explicit dialog listener so Playwright would leave the native confirmation to the human tester. A mistaken tab switch was investigated against the identified test tab instead of being immediately classified as an application logout defect. One archived source-proof file also needed its original captured bytes restored after Git newline normalization. These were tooling/documentation issues, kept separate from product defects and actual owner answers. A trustworthy test report therefore needs source identity, method, actual exit/outcome and preserved failed attempts; the tool's assertion that a check is ready is not sufficient evidence.

Evidence has several distinct levels. The final affected23-case desktop gate, actual22-case Lenovo browser automation, fresh3-case API/PostgreSQL reproduction and31-case main integration gate each have their own source and environment. They overlap and should not be added into one coverage score. Automated requests on a physical tablet are real device execution, but controlled HTTP failures remain test doubles. Jonas's finger scrolling, native dialog choices, rotation, theme assessment and explicit approval answer different questions. He ultimately said “Jeg godkjenner kandidaten og V1-grunnlaget”. That decision accepts the documented local product; it does not make unperformed external security checks pass. [Final integration](../evidence/v1-main-integration-20261029.md).

The privacy and trust boundaries are part of the design. Synthetic PDFs/accounts make repeatable assessment possible without distributing real work documents or credentials. Source-update time, validity, check time and actual road clearance remain separate. Planned time does not move the selected activity, and manual completion does not prove physical work. Fixed server retention, owner/session checks and no private persistent browser cache reduce specific risks; they do not prove forensic erasure, complete accessibility, safe use while driving or real-world time savings.

The completed local V1 is not a certification of its public deployment. A later [separate Access report](../evidence/access-operations-20261029.md) records refusal of the same genuinely signed token after actual expiry and refusal of another active member excluded by the exact email rule. These bounded results concern operational release eb0eee3, not C1/main. Token refusal is observed at Cloudflare, without independent origin-gate observation; the member test does not establish a complete MFA matrix. The owner changed the team domain during the exercise, so the report explicitly preserves that configuration change and repeats the relevant control. An initial login without observed MFA and the later fresh Authenticator flow are both retained. The remaining external timing/network/DNS/OS checks O3–O6 are still open in the [remaining-work register](delivery-readiness.md). This illustrates why a completed bounded exercise must not be turned into general security assurance. Bounded isolated tests and broad OS/supply-chain claims need their own defined evidence. Integrated Ubuntu has separate version-specific operational evidence; it does not close O3–O6.

The final documentation preparation addresses a smaller reproducibility issue as well: the assessor must remain in one exact delivery checkout with both the accepted product and its final evidence. C1 is the product reference; it is not, by itself, the complete later documentation package. Keeping the running source, README, evidence and final commit identity connected makes the assessment more inspectable and reduces reliance on conversational memory.
