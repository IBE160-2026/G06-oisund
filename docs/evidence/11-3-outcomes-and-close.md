## Technical contracts

Migration `010_outcomes_and_closure.sql` is additive: it relaxes the existing exact retention check to a non-extending bound, adds nullable lifecycle `ended_at`, extends lifecycle constraints to active revision one / terminal revision two, and creates outcome values, per-workday outcome revisions and two receipt tables. Existing unstarted plans still have no lifecycle row; existing first starts/receipt JSON are preserved. The planned maximum is still derived from immutable `final_end + 7 days`; current `expires_at` may be shorter.

`GET /workdays/{id}/outcomes` returns the complete ordered exact membership, projecting absent values as unregistered. `POST /workdays/{id}/outcome` takes operation ID, expected outcome revision (`expected_revision`), `expected_lifecycle_revision`, member ID and typed outcome. `POST /workdays/{id}/close` takes operation ID, expected lifecycle revision (`expected_revision`), expected outcome revision and `ended | aborted` action. Corresponding operation lookup routes retain the existing `{operation_id,result}` receipt shape. `GET /workdays/{id}/recap` returns plan, lifecycle, outcomes and bus under one parent lock.

The existing account/parent transaction ordering serializes all writers and deletion. Closure atomically saves the first ending time and `min(existing expiry, planned final end + 7 elapsed days, first server ending + 7 elapsed days)`. Related live operation metadata is shortened; historical receipt JSON is untouched. Parent authorization/expiry is checked before replay and again at completion. Old receipts cannot replace current lifecycle authority or extend a timer. Confirmation lookup continues to project the current plan dynamically. New tables cascade with the parent and join startup/hourly cleanup.
