## Future restore/rollback procedure and unresolved mechanism

These steps describe future preparation, not authorization to execute on production. Before any change, inventory installed releases/migrations, establish the intended snapshot/account consequences and schedule a maintenance window. Existing fixed helper primitives can create a fresh backup and verify a disposable restored copy:

`sudo -n /usr/local/sbin/bussassistentctl backup`

`sudo -n /usr/local/sbin/bussassistentctl verify-restore`

After a separately authorized outage, `sudo -n /usr/local/sbin/bussassistentctl stop` stops application/database services. The deployment procedure separately stops the tunnel before changing releases. These commands alone do not install a restored database or make credential authority safe. Preserve the current verified snapshot and keep traffic closed when restoration is necessary.

Ordinary `rollback SHA` is available only for installed candidates with identical migration files; v1.0.1 main lacks015 and is rejected. Old source reading the new schema/hash is compatibility evidence only. `restore-initial` explicitly refuses an existing deployment/data-ready marker and nonempty database. `verify-restore` proves a disposable copy, not replacement of live data. Do not delete markers, repoint production volumes, bypass migration equality or substitute ad hoc SQL.

**Technical release prerequisite, requiring a separate scoped owner decision/authorization:** a reviewed existing-deployment restore mechanism with ingress/write quiescence, archive integrity, atomic failure handling, all-account session/proof invalidation and verification before reopening. The installed helper has no such replacement/invalidation interface. Per-account recovery-revoke leaves sessions and passwords unchanged; password recovery needs the normal app endpoint, while the synthetic S4 settlement calls an internal service in a disposable process. Therefore those existing primitives cannot alone provide a production quiesced all-account old-hash settlement procedure. No guessed credential policy, new administrative feature or broad sudo command is added here.

What can be prepared and tested now is complete within the available primitives: actual restricted-runtime snapshots, restore/repeat/restart, all-session/proof invalidation and synthetic old-hash settlement; ordinary helper backup/verification and migration guards are retained and reviewed. These tests do not install the missing production interface. The exact missing decision is how to settle restored credential authority when a trustworthy current credential snapshot exists versus when it does not: retaining trustworthy current hashes or requiring qualified recovery by every affected user have different consequences, especially for unavailable users. No forced-reset/account-lock policy can be inferred. The owner must select that policy and authorize the bounded privileged existing-deployment replacement/invalidation mechanism before it can be implemented and qualified. This is a concrete product/operations decision, separate from physical-device acceptance.

For every restored account, identify older password authority and obtain the required qualified settlement or explicit informed owner decision while traffic remains closed. Independently verify expiry/cleanup, identities/ownership/content/deadlines/receipts, rejection of every stale session/proof/superseded password and proper new login before an explicit reopening decision. Backup may lose later business writes. This missing technical mechanism cannot be closed by signing the personal checklist; synthetic feasibility does not make it deployed recovery tooling.
