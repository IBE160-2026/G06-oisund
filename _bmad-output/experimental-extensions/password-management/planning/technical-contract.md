# Implementation contract and bounded defaults

Read with the SPEC and epic. The owner decided scope, administrative SSH recovery, all-device logout and separate delivery. The concrete mechanisms/defaults below are engineering proposals for implementation and review, **not new owner-approved product decisions**. No unresolved choice prevents starting S1 after separate authorization. Operational handoff qualifications block real issuance/release if they fail, not creation of synthetic tests.

## Baseline, code map and stable interfaces

Fetched main remains `5cee9e03d03d2c9c165c7f8fec64aa3e146959ab`. React private access is `frontend/src/PrivateAccess.tsx`; business wrappers/dirty guards include `PrivateDrafts.tsx`, `PrivateConfirmation.tsx`, `PrivateWorkdayView.tsx` and recovery helpers. Password/session code is `backend/app/auth.py`; HTTP boundary/DTO/cookies are in `private_main.py`; operator actions in `manage.py`; migration/cleanup in `private_storage.py`; owner serialization begins in `draft_storage.authorized`. Inspect all callers/direct session SQL, including imports, before the locking change. Existing backend `run.py` disables access logs/proxy-header trust; gateway strips forwarding headers and has access logging off. Do not weaken those controls or infer real end-user IP through the proxy.

Proposed names, subject to consistent implementation naming: `POST /auth/password/change` accepts current_password/new_password/confirmation, session-derived target only; `POST /auth/password/recover` accepts username/code/new_password/confirmation without a valid app session. A live app session on recovery receives a neutral conflict requiring explicit logout; an expired cookie is not recovery authority and may be cleared. Both return only a bounded success acknowledgment, clear the caller's obsolete app cookie where applicable, and never issue a session. Preserve cookie flags, no-store, Origin/CSRF and safe validation handler. Wrong current password is a typed validation failure; code failures all use the same generic 400 shape; live-session requirement 401, CSRF 403, validation 422, throttling 429, unavailable 503. Do not expose raw framework validation input. UI confirmation mismatch can be local, but server policy remains authoritative.

Use existing 12–256-character scrypt policy without password trimming; do not introduce a new password-strength policy. Fresh salt per replacement; no plaintext in DB. Password hashing verification helpers should not call `authenticate`, which creates sessions. Recovery codes are random ≥256-bit bearer secrets; SHA-256 digest-only storage is suitable for these high-entropy values, distinct from scrypt for human passwords. No JWT, email link or general-purpose reset session is required.

## Transaction protocol: correctness before cleverness

Implement one per-account PostgreSQL transaction-scoped advisory lock, acquired before any session/account/private row lock for an operation that can authenticate, mutate credentials or use account authority. A stable namespaced UUID-derived lock key can serialize collisions safely; never use Python's process-randomized hash. A session token may be read without a row lock only to discover its owner; acquire the account gate, re-read/validate the session and then take row locks in existing business order. The unauthenticated discovery does not itself grant authority.

Login resolves username and acquires the same gate before verifying the current stored hash and creating a session. The simplest initial implementation keeps bounded password verification inside this gate; no separate credential-version column is needed solely for this race. If profiling later moves hashing outside, a locked recheck of the exact observed credential hash/version is mandatory. A stale successful verification cannot insert a session after replacement. Unknown usernames take bounded dummy verification without acquiring a fake account lock.

Change/redeem: admit attempt → account gate → fresh session/current-password or proof/binding/expiry checks → update hash → consume/revoke all proofs (once S2 exists) → delete every account session → commit. Return only after commit. S1's transaction service must allow S2 to integrate proof invalidation in the same transaction; S1 does not create future tables. Two current-password changes using the old password cannot both succeed. Code redeem locks/conditionally consumes the active proof; at most one wins. Issuance/revoke use the same account gate, and issuing a code does not revoke sessions. Expiry is checked against DB time immediately at acceptance, including after expensive hashing; a proof expired while waiting/hashing must fail.

Inventory and adapt cleanup/logout/read/private mutation paths so none holds session/business row locks and then waits for the account gate. Cleanup works in bounded account-scoped transactions with that gate before deletes; preserve each business retention rule. Global rate-admission locks are acquired/released in their own short transaction before account locking and are never reacquired while holding account authority. Failed attempt counters therefore cannot roll back with credential rejection. Never acquire gates for several owners in arbitrary order; avoid cross-account transactions or use documented stable order. Verify actual PostgreSQL concurrency across workers, including late login responses. A response from a login committed before reset may arrive late with an already revoked token; its next authorization must fail and frontend guards must not resurrect private content.

This is a proposed lock protocol to be proved by S1, not a claim existing code already complies. No retained old-session authority or offline lease is introduced. Saved business operations committed before reset remain historical truth; no pending client command is silently replayed after credential change or across accounts.

## Bounded defaults for deterministic tests

| Parameter | Initial engineering default | Test boundary |
|---|---|---|
| Recovery code lifetime | 30 minutes from DB issuance time | usable before expiry, rejected at/after; no extension by reading/retry |
| Active proof | one per account, purpose password-recovery | reissue atomically revokes old proof; redemption consumes all outstanding proof |
| Change/recovery admission | separate purposes; max 5 admitted submissions per normalized account bucket per 15 minutes | attempt 6 throttles, including concurrent workers; valid submission also consumes budget |
| CPU/storage guard | per-purpose global 100 and proxy-address 20 admitted requests/15 minutes | check global before creating new user buckets; proxy may group both real users |
| Operator issuance | 3/account/hour | attempt 4 rejected; revocation remains possible; no undocumented override |
| Recovery metadata cleanup | consumed/revoked/expired digest removed within 24 hours | live-code acceptance never depends on cleanup having run |
| Minimal audit | proposed 30 days | purge according to bounded retention; no credential/code/cookie/body fields |

These bounds make stories testable without asking the owner to design algorithms. Compare to actual load in isolated tests; propose changes if availability/security needs conflict and record them rather than claim owner approval. No availability SLA is promised. Code rejection must not reveal account existence through message/status or obviously different work; malformed shape may use the same bounded rejection path. Evaluate timing distributions under controlled known/unknown/wrong-account tests; do not promise identical network latency. Preserve separate existing login budgets.

## Operator interface and secret handoff

Proposed CLI `python -m app.manage recovery-issue USERNAME` / `recovery-revoke USERNAME` through the existing privileged SSH/container workflow. Username is not a secret, but no password/code is accepted in an argument/environment variable. Resolve exact normalized account and show username+UUID; require typing the complete resolved username to confirm. No implicit “my account”: Jonas selects his own app username explicitly. Existing independent SSH/host permission is the authority, without an app cookie or an extra app admin account. Record actor as the authenticated operator context/configured operator identity, distinguishing unverified operator labels from verified SSH audit identity; do not fabricate per-person attribution from a shared OS account.

Only an interactive controlling terminal may receive the generated code, directly rather than through stdout/stderr, after the DB commit. Refuse piping, redirecting, missing terminal and noninteractive execution. Present expiry with time zone, show once and clear the terminal display on acknowledgment; do not rely on display clearing to erase scrollback/recordings. Preflight explicitly checks terminal transcription, SSH/session capture, wrappers, CI execution, screen recording and shared screens. TTY detection alone cannot establish these are absent. The qualified command should not emit code to container service logs. Use only synthetic markers when testing logging surfaces. If a capture-free path cannot be established, do not issue/disclose a real code; record the concrete blocker.

The command stores a digest, not retrievable plaintext. An interrupted or unconfirmed handoff means explicitly revoke/reissue; do not print the same code again from storage. If DB commit succeeds but terminal delivery fails, attempt safe revocation and report uncertain issuance without showing secrets; operator revoke settles it, and TTL bounds any unresolved proof. No temporary plaintext file, general clipboard helper or recovery-code audit entry. The operator transmits the code only after identity confirmation via a previously established direct channel, without putting it in tickets/chat transcripts/logs. A copy/paste handoff requires explicit clipboard-history/cloud-sync awareness; prefer direct controlled entry for the two-person setting.

Runbook: confirm identity using personal recognition or independently established callback/contact, never username alone; confirm exact account; issue; let the user choose their own password; revoke/reissue if delivery fails; do not promise immediate support when Jonas is unavailable. For Jonas's own account, possession of his independent authorized host access enables the same command without the forgotten app password. If SSH is lost, stop app recovery and use the separate host access procedure; if outer Access is lost, app reset does not bypass it. The owner must verify the practical contact/handoff path before live use; this is a bounded operational gate, not a reopened choice of email or dashboard.

## Browser/offline and migration boundaries

Before voluntary change, dirty edits must be saved/cancelled and uncertain business operations reconciled; never silently discard them to reach settings. After reset from another device, security revocation wins: clear private memory on detection and explain unsaved edits may be lost. Existing volatile pending metadata is not durable sync state. Reauthentication to the same UUID can use existing authorized server receipts; do not persist private proposals or secret requests to support recovery. BroadcastChannel only reaches same-origin tabs, not remote devices. Offline devices cannot receive immediate revocation; their next authorization is denied. BFCache/visibility/late replies must follow existing generation/revalidation guards.

Add recovery schema in S2 only. Keep account UUIDs and every business FK/data row. No account recreation, forced reset or email enrollment. If any account-column change is actually needed, fix positional `INSERT INTO accounts VALUES` before the migration and test old/new provisioning. S1's proposed lock-based design avoids an unnecessary credential-generation migration. Enforce proof purpose, owner and expiry in DB-backed service; cleanup failure cannot authorize expiry.

Rollback/restore can resurrect credential state from a backup. The future runbook must quiesce traffic, restore/verify business data, invalidate all restored app sessions and proofs before reopening, and explicitly handle old password hashes restored from older snapshots. Compatibility with older code is verified, not assumed; no new field may be the only revocation barrier ignored by rollback code. Host/outer Access control remains independent. Release/restore operations themselves are outside this planning task.
