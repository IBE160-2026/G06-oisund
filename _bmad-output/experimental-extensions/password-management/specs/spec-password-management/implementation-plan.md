# Proposed implementation and delivery plan

**Owner decisions recorded on 2026-10-31:** administrative one-use codes, Jonas as operator, initially Jonas and the course teacher, logout on all devices for both flows, and separate delivery. Technical details remain recommendations unless explicitly identified as decided. No implementation or production changes are authorized or have been made.

## Selected minimum scope

Deliver own-password change plus operator-assisted forgotten-password recovery. The operator verifies the requester through an independently established channel and issues a random, account-bound, short-lived one-use recovery code; the user sets their own new password in the application. This reuses the existing operator provisioning boundary without adding email collection, an admin role model, a mail provider or a general profile system.

The confirmed two-person initial scope and Jonas taking responsibility support this minimal approach. Public availability is outside the initial scope and is not committed to; no public signup, scaled support organization or 24/7 service is planned. A wider audience would require a new scope/administrative-capacity decision. Define the actual support contact and identity-check procedure before use. Never recover an account on knowledge of username alone, a message from a newly claimed address, personal trivia, or possession of an unrelated outer Access account.

## Recovery alternatives

| Concern | Assisted recovery (selected initial scope) | Self-service email |
|---|---|---|
| Identity | Operator checks known person in person or calls back using a previously established trusted contact; records method/result, not secret evidence. If verification fails, no reset. | Verified address already bound to the application account; control of mailbox is recovery authority, with compromised/lost mailbox fallback. |
| User model | Existing accounts unchanged; add recovery-proof storage and safe audit metadata. | Nullable email/pending email/verified-at or dedicated contact table; verification lifecycle, change-of-address protections, normalization/uniqueness policy. |
| Operations | Named operator, coverage, secure code handoff, revoke/reissue procedure and access audit. No mail service. | Provider credentials, sender domain, SPF/DKIM/DMARC, quotas, bounces/spam, outage handling, delivery monitoring and credential rotation. |
| Cost | Operator time per recovery; no incremental mail-service bill assumed. | Provider/domain and maintenance costs plus operator fallback; actual price depends on chosen service/volume and is not estimated here. |
| Convenience | User waits for support but needs no email account in this product. | Usually faster and available without operator, but enrollment and lost-mailbox cases add friction. Delivery is not guaranteed. |
| Complexity | Medium: most work is secure mutation/concurrency and frontend recovery. | Substantially higher: same core plus contact trust, delivery and operations. |

### Assisted flow

1. “Glemt passord?” displays the approved support route and “Har du fått en engangskode?”. It does not query whether a username exists.
2. Operator verifies identity against the known account using the approved procedure. Existing SSH/operator access is the administrative boundary, explicitly including Jonas issuing a code for his own app account without app login/current app password; do not grant application users administrator rights. Provide an operator command to issue, replace or revoke recovery proof with explicit target confirmation. No generic SQL edits.
3. Generate 32 random bytes encoded as a copy/paste-friendly code, bound to account UUID and recovery purpose. Proposed lifetime: 30 minutes. Store only a digest and timestamps/status; at most one active code per account. Issuing a replacement invalidates the prior code. Deliver through the verified channel. No temporary password and no password change at issuance.
4. Secret output must be a one-time non-recorded operator handoff, never ordinary stdout captured by logs, CLI arguments, shell history, audit payloads, tickets or this chat. Qualify the actual terminal/session-recording setup; if safe handoff cannot be established, stop issuance. Clear clipboard/display after handoff. An operator with database/host access remains a highly trusted actor.
5. User enters username, code and new password twice. Normalize username as login does; require both code binding and intended username. If logged into another account, require leaving that workspace explicitly first; never silently switch or replace another account's password.
6. One successful transaction updates password hash, consumes all active recovery proofs and revokes all application sessions for this account. Return success without automatic login; user logs in with the new password. GET/opening the form never consumes a proof. Failed attempts do not change credentials or revoke sessions.

Codes avoid secret-bearing URLs and outer Access redirect complications. If links are added instead, use a fixed canonical HTTPS origin, high-entropy token, no third-party assets/referrers and no token in access/error/analytics logs. Prefer a fragment read once into memory and immediately removed from browser history; test survival through outer Access login explicitly. Query-string tokens are not acceptable without verified end-to-end redaction. A scanner opening a link must not consume it.

### Conditional email extension

Do not infer an address from username or auto-trust Access headers. Existing users begin with no recovery address and retain normal access. Enrollment requires an authenticated session plus current password, then a distinct expiring email-verification proof. Only the verified address becomes eligible for recovery. Address changes require reauthentication, verification of the new address, invalidation of old recovery proofs and notification of the old address where available; a typed address alone cannot replace recovery authority. Lost access to both password and email remains an operator identity-verification case.

Use a transactional mail provider rather than running an SMTP server. Choose provider, account owner, volume/budget and sender domain before implementation. Keep API/SMTP secrets in restricted, host-managed files mounted read-only following the existing `/run/secrets` pattern; never commit, bake into frontend/image, pass in command arguments or request secrets in chat. Define rotation, backup access and redacted failure reporting. Current private API network is internal: design narrowly scoped mail egress or a small sender boundary, not broad unrestricted connectivity.

Email request responses must use the same status/message for unknown, unverified and eligible accounts (“Hvis kontoen kan gjenopprettes på denne måten, får du videre instruksjoner.”), with comparable response timing independent of provider latency. Bound per-account/global/IP requests and mail volume. If asynchronous sending is used, handle retry/idempotency and protect any queued secret payload with short retention and encryption; avoid introducing a general queue platform solely for this feature. A delivery failure must not lock the account or change its password. Notification after replacement contains no password or recovery proof. Detailed provider/delivery design is deferred, not implicitly part of the minimum.

## Security and concurrency design

- Reuse salted scrypt and constant-time verification, fresh salt for the new password, 12–256 input bounds and strict DTOs. No trimming/normalization of passwords. No forced changes for existing users or arbitrary periodic rotation. A broader password-policy change is separate scope.
- Own-password endpoint derives target exclusively from the live session, never a client-selected account ID. Recovery proof grants only replacement for its bound account, not a session or general private access. Both routes retain Origin/CSRF, canonical host, no-store and body limits.
- Add persistent per-purpose bounded attempt admission before expensive hashing; use the concrete initial limits in [technical contract](../../planning/technical-contract.md). Count admitted submissions consistently, including failures, with account/global/proxy buckets; commit counters separately so rejected credential transactions cannot roll them back. Unknown-user buckets are bounded by global admission. Existing login budgets stay separate; no permanent anonymous lockout or trust in arbitrary forwarding headers.
- Recovery rows need random identifier/digest, account FK, purpose, created/expiry/consumed-or-revoked timestamps; index expiry and enforce one active proof per account. TTL uses server/DB time, not client clock. Remove expired/consumed secret digests through existing cleanup within a proposed 24 hours; expiry is enforced immediately regardless of cleanup success. Minimal audit events retain actor/account/event/time/result for a proposed 30 days, subject to owner operational needs, with no request bodies, passwords, codes, links, cookies or verification evidence. Hashing a high-entropy token is distinct from hashing human passwords.
- Password replacement, proof consumption and revocation must be one transaction, with row locking/conditional update so two concurrent completions yield exactly one success. A validation error rolls back everything. A new code, either password replacement or explicit operator revoke invalidates all older recovery proofs. Requesting a code alone never resets passwords or kills sessions.
- Existing session-then-account locks conflict with a naive account-then-delete-all-sessions reset. Design and document one consistent lock order for auth, private storage and cleanup before coding; do not bolt account-wide deletion onto current locks. Proposed approach: a shared per-account transaction lock acquired before session/account row locks by every affected path, revalidate session after acquisition, then revoke. Anonymous session lookup may discover owner without a row lock but must be rechecked inside the lock. Qualify reads, writes, logout, cleanup and imports, not just new endpoints. Existing global admission locks must have a documented compatible order too.
- Login currently verifies and inserts without account-wide reset serialization. The [technical contract](../../planning/technical-contract.md) now specifies the simplest proposed fix: acquire the shared account gate before checking the current stored hash and creating a session; all credential and private authority paths use the same order. A credential-version column is not mandatory. If verification is moved outside the gate, recheck the observed hash/version under the gate. Concurrent login/reset/private mutation tests are mandatory; a pre-reset committed business action remains history, but revoked authority cannot commit afterward.
- Owner-approved policy is logout of **all** application sessions, including the current session, after both change and reset. This avoids a special retained-session path. A future “keep this device” choice adds rotation and race testing and is not the minimum. Clear browser cookies where possible; server revocation is authoritative across devices.
- Day access is derived from session + owner + nonexpired workday, not a separate grant today. Revocation removes that access; saved workdays, active shift state, receipts and deadlines remain unchanged. If future day tokens/offline leases are introduced, bind them to the same credential/session generation and invalidate them too; do not invent such a subsystem now.
- Broadcast invalidation to other tabs, increment frontend generations, discard late replies, clear sensitive form fields and private views. Remote devices learn revocation at their next server check; an already displayed offline screen cannot be remotely erased instantly. Preserve existing hide/recheck behavior and document that limit honestly. No offline password action, durable code storage, service-worker caching or automatic replay after reconnect.
- After uncertain password submission, clear secrets and require explicit login/recovery; do not queue it or report success without a valid receipt. Existing ordinary workday operation receipts remain owner-scoped and can be reconciled after same-account reauthentication; do not silently replay an unresolved business command under a different account.
- Existing outer Access/IdP sessions are independent. An application password reset does not revoke them. Suspected compromise also requires the operator's existing outer Access revocation procedure; do not promise an application reset repairs a compromised IdP account.

External cross-check (read 2026-10-31): [OWASP Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html) supports neutral responses, random expiring single-use proofs and session invalidation. [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) lists the existing scrypt parameter combination among supported work-factor options. Local TTL, budgets, locking and rollout choices above are project proposals, not quotations or claims of certification.

No real user forced to enroll email or recreated. New users and old users use the same flows after rollout. Back up and prove isolated restoration before future migration; compare synthetic pre/post row identities/content and legacy login. Never run synthetic reset/setup against a real database.

Update operator guide, user guide, Ubuntu deployment/secret/network instructions, recovery/incident runbook, data-retention/cleanup documentation and test recipe. Minimum mode needs no new external service or production connectivity. A compatible code rollback must continue honoring credential revocation; simply deploying V1 code that ignores a new version field could revive authority. Prefer deletion of old sessions as well, invalidate sessions/recovery proofs at controlled rollback/restore, and require login. Restoring an older backup can resurrect old password hashes/tokens: document deliberate recovery and forced session/proof invalidation, not an unqualified zero-impact restore promise. Rehearse rollback without truncating account/business data.

## Selected delivery and rationale

The owner selected a **separate password-management delivery**, with own change and assisted recovery forming the minimum complete user scope. It has no functional dependency on automatic-notice ingestion, but requires concentrated security, migration and cross-session regression tests. Automatic notices has different source-access, mapping, polling and provenance risks; coupling completion dates would increase coordination and test scope without reducing password work.

If a common release is later chosen, keep independent branches/specs/acceptance and separate tests. Before publication integrate on then-current main and test auth revocation against notice fetch/read/review overlays, concurrent refresh/save, 401/unavailable recovery, owner isolation, migration ordering, cleanup, tablet shell/navigation and the actual Ubuntu gateway/API/database package. Public collection must neither grant private access nor recreate deleted/expired private overlays. One feature's test completion never approves the other. No version number is allocated in this planning work; a later release decision must set it.
