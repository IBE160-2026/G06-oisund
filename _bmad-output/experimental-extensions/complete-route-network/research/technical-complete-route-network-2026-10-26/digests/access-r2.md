# Access research round 2
Accessed 2026-10-26; supplements access-r1.md. No datasets downloaded. Findings are paraphrases; no direct quotations.

## Updated granularity observation
[A1, revisit] https://developer.entur.no/open-data/timetable . Search-index retrieval exposed the table while direct page retrieval still showed Loading. The cached table lists Troms (Troms fylkestrafikk) and Finnmark separately, each with NeTEx and GTFS; Norway alone shows GTFS Basic. It exposes no city-level archive. Cached Troms import timestamp was 2026-09-24 14:53:55; do not report this as live freshness on 2026-10-26. Exact timetable ZIP links still unverified. This is evidence of offered regional/provider granularity, not proof that the pilot's complete city network matches that provider boundary.

[B1] Timetable import metadata, https://developer.entur.no/apis/timetable-import-info and https://developer.entur.no/apis/timetable-import-info/timetable-import-info (publication/modified dates not displayed). Open NLOD API with ET-Client-Name. GET https://api.entur.io/timetable-public/v1/timetable-import-info/import_date returns latest successful import dates by provider codespace; suffix /{codespace} selects one. Dates represent original provider import, which differs from nightly archive regeneration. Inference: track both import date and archive/hash snapshot; an unchanged original import does not alone mean unchanged daily archive bytes.

[B2] Raw timetable data, https://developer.entur.no/apis/raw-timetable-data and https://developer.entur.no/apis/raw-timetable-data/raw-timetable-data (dates not displayed). Catalog classifies this under Partner APIs, separate from public exports. Documents original-provider datasets, version enumeration (importKey and creationDate), exact version and latest endpoints; examples require Authorization Bearer. Retention length is unspecified. Download Accept must be application/octet-stream or wildcard; application/zip causes 406. dsjcompatibility selects legacy NeTEx 1.15 or new 1.16 structure during migration; absent requested variant falls back to default. The rendered base/path duplicates timetable-data; verify the resolved endpoint before implementation. This is a potential partner-history source, not a public historical retention promise.

[B3] Timetable Management datasets, https://developer.entur.no/apis/timetable-management/datasets (dates not displayed). Private filtered download adds Block data, DeadRuns and publication-restricted Lines/ServiceJourneys beyond public exports. It filters expired and unsupported content and excludes failed validation. Inference: define completeness as published passenger service, not every operational movement. The same documentation signals a 1.15-to-1.16 DatedServiceJourney structure migration. Preserve parser/schema provenance; API compatibility promises do not prevent data-shape migrations.

[B4] GTFS primary specification, https://gtfs.org/documentation/schedule/reference/ (explicit revision 2026-04-27). Persistent stop_id/route_id/agency_id between versions are advised where possible; this is not an unconditional ID guarantee and does not cover trip_id in that recommendation. Current/upcoming service should cover seven days, preferably thirty; these are specification recommendations, not observed Troms coverage. Service days may exceed 24:00. Shapes are not universally mandatory. Inference: inspect actual coverage/calendars and retain source IDs plus snapshot identity; do not promise geometry or treat clock times above 24 hours as invalid.

[B5] Nordic profile, https://entur.atlassian.net/wiki/spaces/PUBLIC/pages/728891481/Nordic%2BNeTEx%2BProfile (updated 2021-04-29). Official landing page describes a focused NeTEx subset and links separate framework, stops, network and timetable sections. Landing page does not establish eternal ID semantics.

[B6] Realtime, https://developer.entur.no/open-data/realtime (modified 2026-08-31). Separate from basic timetable data. TRO is listed as Troms provider codespace; supports SIRI ET/VM/SX and GTFS-RT trip updates/vehicle positions; the displayed GTFS-RT alert column is empty for TRO. GTFS-RT updates every fifteen seconds with provider filtering by datasource; this does not establish availability/completeness of every route's realtime. SIRI Lite documentation limits four requests/minute. Inference: real-time should overlay, rather than define, the planned-service inventory.

## Recommendation after both rounds (inference)
Acquire the Troms public NeTEx regional/provider snapshot and appropriate NSR stop versions; apply an explicit line/mode/geographic inclusion rule locally, retaining references and provenance. Confirm a city-bus route manifest and pattern/calendar coverage against targeted API queries. Retain immutable snapshots for historical comparison. Offer GTFS as a simpler derived import/projection only when documented data loss is acceptable. Do not substitute trip search or realtime for complete scheduled-network enumeration. Consider the partner raw history API only if access and retained versions are established.
