## User flow and copy

1. **Day:** Open the confirmed day. Existing bus entry, `Start skift`, selected member and preparation navigation remain distinct. Before Start, consultation/selection works. Owner-approved: outcome controls explain `Start skiftet før du registrerer utfall`; terminal actions are unavailable with an explanation.
2. **Selected activity:** Keep exact ordinal/type/route/direction, planned Oslo calendar times and known/unknown places. Add a clearly labelled `Registrert utfall` area, separate from previous/next and selection. A labelled choice offers `Ikke registrert`, `Fullført manuelt`, `Hoppet over`, `Avbrutt`, followed by explicit `Lagre utfall`. Default is `Ikke registrert`; choosing a form value is only a proposal until saved. Support all real members, including individual grouped pauses. Gaps are not registrable activities. Saving never chooses/opens the next activity or changes Start/bus/source facts. Return to `Ikke registrert` is an explicit correction, with no inferred physical completion or required explanation field.
3. **Return to day:** Restore focus to the member; show saved outcome labels in the day, including a cue inside collapsed pause groups. `Avslutt skift` and `Avbryt skift` lead from day/shift navigation to a dedicated confirmation screen. Existing `Lukk planen` only closes the view; distinguish this clearly from terminal closure.
4. **Closure confirmation:** Show the chosen action, first actual start, proposed terminal meaning, saved outcome counts and remaining unregistered members. Explain that unknowns stay unregistered and closure cannot be resumed/edited. Offer `Bekreft avslutning` or `Bekreft avbrudd`, and prominent `Tilbake uten å avslutte`. Cancel changes no server data and returns focus to the invoking control. Unregistered members do not block ending. Unresolved/unsaved writes must be settled, explicitly discarded when known unaccepted, or revisited before a new closure attempt; uncertain commands cannot simply be discarded as failed. Stale outcome counts require refreshed review and another explicit confirmation.
5. **Recap:** Only an authoritative terminal result opens a separate read-only screen. Show `Skift avsluttet` / `Skift avbrutt`, neutral `Takk for i dag`, service date, planned start/final end, first actual start/server ending with calendar dates, saved bus where known, per-state counts and ordered member outcomes. Counts include unregistered members and sum to the exact confirmed membership, not grouped visual rows. Include unknown facts without invented data, expiry, `Tilbake til dagen` (read-only) and clear navigation to preparation/plan lists. No completion percentage, score or claim that the day was physically driven.
6. **Reopen:** An authorized terminal day opens the recap; read-only day/member consultation stays possible without persisting another selection. Existing saved selection is retained. Terminal previous/next consultation, if exposed, uses transient presentation only. No bus/outcome/Start/selection mutation is available. Existing explicit deletion remains a separate privacy operation, never an end/abort substitute.

One primary screen is visible at a time. Keep required controllers mounted or move their ownership above screen switches; never hide the only check/retry action. Preserve unsaved editor/time/bus/outcome input during safe internal navigation. Meaningful heading/focus and return focus must work with keyboard and touch. Long/enlarged content scrolls without clipping; no new routing dependency or private route cache is required.

## Approved state and write contracts

| State | Consultation | Outcome writes | End / abort |
|---|---|---|---|
| Confirmed, not started | Existing selection and read-only detail | Unavailable until Start | Unavailable; never start implicitly |
| Active | Existing selection/detail | Save/correct exact-member outcome | Explicit review and confirmation |
| Ended / aborted | Read-only day/detail/recap | Rejected server-side | No new transition or restart; original accepted retry remains resolvable |
| Unknown / denied / expired | Existing guarded visibility/revalidation | No assumed authority | No assumed success or bypass |

Extend the lifecycle authority introduced in 11.1, rather than adding a competing shift. Proposed current lifecycle includes state `confirmed | active | ended | aborted`, unchanged nullable `started_at`, nullable `ended_at`, revision and current effective expiry. Legacy missing lifecycle rows remain unstarted revision zero; existing active rows keep their first start. Terminal status/time cannot change once accepted.

Store outcomes independently from immutable confirmed content and selected activity. Use a typed enum (`unregistered`, `completed`, `skipped`, `interrupted`), validated exact membership and a per-workday outcome revision. Missing entries project as unregistered; explicitly clearing a prior outcome remains revisioned. No source activity rewrite, synthetic timestamps for physical completion or activity-type exclusion.

Proposed outcome command carries stable operation ID, expected lifecycle/outcome revisions, member ID and outcome. Closure carries stable operation ID, expected lifecycle and outcome revisions from its reviewed screen, and terminal action. Generate operation identity before sending; store bounded immutable accepted receipts with owner/workday/payload binding, authorized lookup and same-body retry. Reusing identity with changed action/content conflicts. Use existing per-resource 2,000 live-receipt/account ceiling unless a documented contract reason requires another bound; accepted retries do not consume a new slot. Capacity rejection changes nothing and leaves a cancellable, known-unaccepted proposal.

Use the existing owned-workday transaction lock to serialize outcome, closure, Start, bus, saved selection and deletion. Check session/ownership/expiry again at atomic acceptance. The first matching active→terminal transaction wins; same accepted operation returns its original result. A fresh competing close/end/abort operation conflicts and loads authoritative terminal state; it cannot change terminal reason/time. An outcome accepted before closure is included; one arriving after closure is rejected. Expected outcome revision prevents confirming stale displayed counts. Start cannot revive terminal work, including its existing special expected-revision-zero convergence path.

All terminal mutation paths reject new bus/selection/outcome/Start writes server-side, including stale tabs. Accepted historical retries may report their original effect but must reconcile with current authority and must never re-enable editing. Recap should read plan/lifecycle/bus/outcomes consistently under the workday lock or equivalent snapshot, avoiding mixed pre/post-closure results.

## Retention and compatibility dependency

Closure must atomically record state, first server ending instant and `min(existing_expires_at, planned_final_end + 7 days, server_ended_at + 7 days)`. The seven-day durations are elapsed server-time durations; display dates in Europe/Oslo. Ending after planned end cannot extend retention. Keep the planned maximum and historical confirmation facts distinguishable from the shortened current deadline.

This requires coordinated schema and reader work, not just a new closure endpoint:

- Migration 009 constrains lifecycle to active/revision 1; extend additively with valid confirmed/active/terminal field combinations, outcome/receipt tables and cascade cleanup. Do not change applied migrations or reset ordinary data.
- `WorkdayRecord.fixed_deadline` currently requires exact planned-end+7d; `workday_storage.presentation`, list/reopen, confirmation lookup and frontend validators assume it. Define current effective expiry separately from the preserved planned maximum and ensure current record projections accept the earlier terminal deadline. Keep old confirmation policies and accepted receipt payloads compatible. Record exact additive field/API names before implementation.
- Related operation metadata must expire no later than current workday expiry. Align live receipt deadlines atomically without rewriting historical result payloads; lookup checks the current parent first. An old start/selection/bus receipt carrying an earlier response's longer expiry is historical, never authority to extend visibility. Include confirmation/deletion receipt behavior in this audit.
- The frontend shared hook and parent expiry timer currently require exact expiry equality. Reconcile validated shortening into the parent and all children; do not report it as malformed, keep a stale longer timer or erase an unrelated new draft/confirmation. Handle a shortening discovered through reopen, child read, terminal response or another window. At expiry clear private presentation and deny lookup/retry immediately; startup/hourly cleanup removes outcomes/receipts with the parent.

11.4/11.5 must reuse these closure/deadline guards for future day notices. 11.6 owns integrated recovery, not the correctness of new writes. 12.1 still verifies the complete retention boundary; 11.3 must already implement its own shortening and no-resurrection behavior.
